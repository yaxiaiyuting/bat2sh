## 3. 观察

### 3.1 指纹的模式

1. **"零产物"有三种完全不同的成因，指纹必须能区分**：
   - **真的没行为**（s09：纯时间计算；s06/s11：循环无匹配项）—— `rc=0` + 空产物 = **正确的阴性结果**
   - **环境不满足**（s12/s14/s15：依赖 `E:\`/`C:\Wing`/`nconvert`）—— `rc≠0` + 空产物
   - **采集器/环境把样本搞坏了**（s01/s02/s10：LF 行尾）—— `rc=255` + **stderr 里满是"不是内部或外部命令"**

   > 如果只看"有没有产物"，这三者**完全一样**。是 `exit_code` + `stderr` 把它们分开的。这也是为什么不把"空产物"直接判成失败 —— 那会把 s09 这种**正确答案**误杀。

2. **目录是独立的一类行为**：s03 的 3 个目录**只有靠 `created_dirs` 才可见**。修复前它会被记成"什么都没做"（`batch-samples.md` §4 缺陷 2）。

3. **中文文件名在 guest 内正常工作**：s03 创建的 `C:\poc\samples\樱野` 等被完整记录 —— 说明 guest 侧文件名与清单都走 UTF-8/Unicode 通道，没有被 CP936 破坏。

4. **环境依赖样本的"失败"是稳定的、可复现的指纹**：s12/s14/s15 每次都会以同样的方式失败。**失败本身是有信息量的行为**，不该被过滤掉。

### 3.2 未被覆盖的行为类型（诚实缺口）

| 类型 | 状态 | 原因 |
| :--- | :--- | :--- |
| **注册表写入** | ❌ **未覆盖** | s08 只做了 `reg export`（**读**）。采集器**不观测注册表**（`session-verdict.md` 的 L2 缺口）。语料里 **23.9%** 的样本会改注册表 |
| **进程创建/存活** | ❌ **未覆盖** | `process` 字段仍是空列表。s13/s16 的 `start` **确实**创建了进程（并弹了模态框），指纹只能从"超时"间接推断 |
| **读取行为** | ❌ 结构性不可见 | 清单差分只能看写。s06/s11 的 `dir`/`for` 读取了什么，指纹里没有 |
| **瞬时效应** | ❌ 结构性不可见 | s08 的 `a.tmp`（建后即删）在 before/after 里都不存在 |
| **网络行为** | ⚪ **本轮为 0**（设计如此） | 批量默认 `--network=isolated` ⇒ 全部 `egress_frames=0`。网络行为需逐样本显式 `--network=recording` |
| **服务/账户变更** | ❌ 未覆盖 | 已在 C3（非破坏性）里排除 |

> **覆盖率结论**：能覆盖的是 **文件 + 目录 + 文本输出 + 退出码**四类；**注册表 + 进程**两类完全缺失，而这两类恰好覆盖语料中近 1/4 的"改系统状态"行为。

### 3.3 哪些样本采集"失败"

严格说**没有一个样本是采集失败**（16/16 拿到了完整指纹）。失败的是**样本自身的执行**：

| 类别 | 样本 | 采集器表现 |
| :--- | :--- | :--- |
| 环境不满足（预期内） | s12 s14 s15 | ✅ 完整记录 rc + stderr |
| LF 行尾被 cmd 误解析（**意外发现**） | s01 s02 s10 | ✅ 完整记录 rc=255 + 乱码 stderr |
| 交互式模态框导致超时（**意外发现**） | s13 s16 | ✅ 超时**被记录为行为**（`execution.timeout=true`）而不是基础设施故障 |

## 4. 三个根因级发现

### 4.1 ⚠️ **LF-only 行尾会让 cmd.exe 解析错乱**（影响语料 **26.7%**）

s01/s02/s10 的指纹里 `exit_code=255`，stderr 全是：

```
'T_FILE' 不是内部或外部命令，也不是可运行的程序
'cho' 不是内部或外部命令，也不是可运行的程序
'lims=" %a in (a.txt) do call:han "%a"' 不是内部或外部命令…
```

stdout 显示 cmd **逐行吃掉开头若干字符**，且吃掉的字节数逐行递增（10、11、12…）——典型的**累积偏移**。

**根因不是编码，是行尾**：

| 样本 | 编码 | CRLF | 单独 LF | 结果 |
| :--- | :--- | ---: | ---: | :--- |
| s01 | UTF-8 | **0** | 72 | ❌ rc=255 |
| s02 | UTF-8 | **0** | 55 | ❌ rc=255 |
| s10 | **GBK** | **0** | 23 | ❌ rc=1 + 垃圾 |
| s03 | GBK | 2 | 0 | ✅ rc=0 |
| s04 | GBK | 1 | 0 | ✅ rc=0 |

**A/B 对照实验（决定性）**：把 s02 **只做 LF → CRLF 转换**（内容一字不改），重跑：

| | 原始（LF） | 仅转换行尾（CRLF） |
| :--- | :--- | :--- |
| `exit_code` | **255** | **0** |
| stdout | （空） | `=== FOR /L: Count 1 to 5 ===` … **完整 354 ms 跑完** |
| stderr | 满屏"不是内部或外部命令" | **空** |

> **对 bat2sh 的意义**：语料普查（206 个文件）显示 **55 个（26.7%）是 LF-only**，`Bat-master`/`非常批处理` 里都有（`call-1.bat`、`SETLOCAL.BAT`、`BuildAll.bat` …）。这些脚本**在真实 Windows 上也同样跑不对** —— 这不是 VM 的假象。
>
> **对采集器的意义**：这是**归因问题**，不是采集缺陷。指纹**正确地**记录了"这个样本以 rc=255 失败"，而 `stderr` 的乱码形状就是根因的指纹。**但如果报告只写"16/16 完成"，这 3 个样本会被误读成"复杂脚本"** —— 所以在 `batch-result.md` 里单列。
>
> **未做（明确披露）**：采集器**没有**自动检测行尾并标注。当前靠人工从 stderr 形状识别。改进方向：在 `script` 段里记录 `line_ending`（`crlf`/`lf`/`mixed`）——成本几乎为零，属于**下个 session 的低垂果实**。

### 4.2 ⚠️ `start` 一个不存在的程序 ⇒ **模态对话框 ⇒ 挂到超时**

s13（156.9 s）与 s16（150.1 s）都触发了 120 s 执行超时：

| 样本 | 结尾动作 | 后果 |
| :--- | :--- | :--- |
| s13 `HOTFIX.CMD` | `start "" "E:\软件\…\打开系统自带命令行参考.bat"` | `start` 找不到目标 ⇒ **弹出模态错误框** |
| s16 `范例.bat` | `start "" "BalloonTip.exe" …` | 同上 |

**为什么这是"非交互"筛选漏掉的**：这两个脚本**不含 `pause`/`set /p`**（C1 静态扫描通过），但 `start` 在 GUI 会话里失败会弹**模态框**，而模态框需要一个"人"去点确定 —— 采集环境里没有。于是进程**永不退出**。

> **判据设计上的意义**：`rollback-design.md` §6.2 早已规定"超时是**要记录的行为**，不是基础设施故障"。本轮实证了这条：两个超时被记成 `execution.timeout=true`，**批量继续跑完**，没有阻塞、没有污染。
>
> **代价**：2 × 120 s = 240 s，占批次总墙钟的 **28%**。批量若要提速，最直接的一招就是把 `--timeout` 从 120 s 降到 45 s（正常样本最慢 5 s，余量充足）。

### 4.3 ⚠️ `md %date%` 失败 —— `md` 不认 `/` 作路径分隔符

s07 的 stderr：`命令语法不正确。` + `'\' 不是内部或外部命令`。根因：`%date%` 在 zh-CN 下形如 `2026/09/26 周六`，脚本写 `md %homes%` ⇒ `md 2026/09/26` ⇒ **`md` 把 `/` 当成开关前缀**，不是路径分隔符。（`created_dirs=[]` 因此为空，指纹如实反映。）

> 这是**另一个"环境（区域设置）依赖"的真实样本**：同一个脚本在 `date` 格式为 `MM/DD/YYYY` 的英文系统上会以不同方式失败。`env-audit.md` 把"控制台代码页"列为受控变量；这条说明**日期格式**也该是。

### 6.5 base 完整性
