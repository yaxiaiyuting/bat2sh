| 原始（`bash_check=False`）`bash -n` 通过 | **45/60 = 75.0%** |
| 默认设置下**降级为注释**（即原始语法失败） | **15/60 = 25.0%** |
| 无 TODO 的脚本 | 9/60 = 15.0% |
| TODO 总数 | **256**（`objects` 121 / `misc` 71 / `errorlevel` 41 / `command` 14 / `control_flow` 9） |
| `errors` 层 | 15 条，**全部** `category = syntax`；无未捕获异常（崩溃类 = 0） |

> 关键观察：**TODO 的 47.3%（121/256）是对象模型（`objects`）**——即原理性缺失（D 档），
> 与 v1.5 B1 研究结论「94.4% 静态 TODO 对命令级追踪不可见」一致。

### 2.2 运行时对照（转换产物 vs 原始 pwsh，均沙箱实跑）

| 指标 | 数值 |
| :--- | :--- |
| pwsh 原始成功（rc=0）但转换产物失败 | **20/60 = 33.3%** |
| 两侧同因失败（环境：缺目录/缺兄弟脚本/Windows 路径） | 36/60 |
| 转换产物 rc=0 而原始 rc≠0（反向偏离，静默嫌疑） | 少量（如 `cd-windows`） |

**20 例「转换可归因失败」的根因分类（全部当前复现）：**

| 根因类 | 文件数 | 代表错误（沙箱 stderr 首行） |
| :--- | ---: | :--- |
| **块栈发射缺陷**（`try { if ... elseif ... }` 开链整段丢失） | 8 | `syntax error near unexpected token 'else'` / `path: unbound variable` |
| **输出行未加引号**（PS 裸字符串语句未转 `echo`，被当命令执行） | 4 | `📂/tmp/roi/runs: No such file or directory` |
| **函数调用未转换**（`$x = GetTempDir` → `x=GetTempDir` 字面量） | 3 | `The temporary folder at 'GetTempDir' doesn't exist` |
| **路径/开关透传**（`realpath -a`、`-pathType`） | 2 | `realpath: invalid option -- 'a'` |
| 兄弟脚本缺失（环境，非转换缺陷） | 2 | `check-cpu.ps1: No such file or directory` |
| 算术 / 交互输入（`Read-Host`） | 1 | `Your BMI is / ( * )` |
| 输出中的命令替换（`📂(Get-Item ...)`） | 1 | `⏳ Step 1 ...: No such file or directory` |

**最小复现（块栈缺陷，逐字）：**

```powershell
# 输入
try {
    if ($x)   { $a=1 }
    elseif ($y) { $a=2 }
    else      { $a=3 }
} catch { $b=3 }
```
```bash
# 输出（原始变体，无降级）——try/if/elseif 开链整体消失
set -euo pipefail
else
fi
    b=3
fi
```

对照：**同样结构去掉 `try` 后转换正确**（`if … elif … else … fi` 完整）。
即缺陷触发条件是 **`try` 块内的 `elseif` 链**，而非 `elseif` 本身。

### 2.3 动态追踪可达性（方法 A，60 个脚本全跑）

| :--- | :--- |
| 静态 TODO 总数 | 256 |

## 3. (a) B1 动态追踪 ROI 裁定

### 3.1 可挽回比例

| 口径 | 计算 | 结果 |
| :--- | :--- | ---: |
| **失败级（主口径，任务书原文）** | 转换可归因失败中，追踪能改变的 | **0 / 20 = 0.0%** |
| **TODO 级（乐观上限）** | 运行时可达 TODO / 全部静态 TODO | **45 / 256 = 17.6%** |
| 语法失败级 | 15 例语法失败中可挽回的 | **0 / 15 = 0.0%** |

**为何失败级为 0：** §2.2 的 20 例全部是 **发射/翻译缺陷**（代码生成 bug），
不是「静态分析拿不准、需运行时观测」的语义不确定性。动态追踪的定位是
「用运行时事实消解保守 TODO」（B1 研究 §6），**它无法修复结构性代码生成错误**。
追踪跑得再全，`try{ if … elseif }` 的开链该丢还是丢。

**典型可挽回用例（3–5 例）——诚实结论：本语料上找不到「静态失败→追踪挽回」的实例。**

追踪 *确实* 提供了静态不可见信息的，是以下类型（但均**不发生在失败用例上**）：

| 用例 | 追踪给出的静态不可见事实 | 能否挽回失败 | 备注 |
| :--- | :--- | :--- | :--- |
| `check-gpu.ps1` | Linux 下整个有意义的函数体**零命令执行**（Windows-WMI 死代码） | 否 | 追踪证明「不可达」，但迁移目标恰是这些 Windows 分支 |
| `check-file.ps1` | `sort` 在 pwsh 7 解析为 `/usr/bin/sort`（非 `Sort-Object` 别名） | 否（该脚本本次未失败） | 别名/版本语义差异，B1 研究报告的招牌案例 |
| `check-easter-sunday.ps1` | `[DateTime]` 比较实际执行（分支已知） | 否 | 失败根因是算术发射，非分支未知 |
| `build-repo.ps1` | 12 路分支中只有最后一个 `else` 执行 | 否 | 失败根因是块栈发射 |
| `check-bios.ps1` | `sudo` 被沙箱阻止 → `$model` 为空 → 静默退出 | 否 | 环境扭曲，非转换缺陷 |

### 3.2 工作量复核（与 v1.5 估算对照）

v1.5 归档估算 MVP **1.5–3 人周**（拆分为 7 项：pwsh 下载器 / bwrap 运行器 / shim 生成器 /
trace 归一化 / 分类器 / CLI 表面 / 语料测试）。本次实测**不推翻该工程量**，
但显著下调其**收益**：在 CC0 语料上，它换不回任何一例当前失败。
按更新后的期望收益/成本比，**B1 不值得作为 v1.8.0 主体**。

### 3.3 裁定

## 4. (b) asyncio 流式层重构 ROI 评估

目标：根治 v1.7.0 遗留项 1（socket 阻塞读不可中断，「停止」需等当前空闲超时，默认 30s）。

### 4.1 现状（只读核实）

| 层 | 位置 | 现状 |
| :--- | :--- | :--- |
| Transport | `core/api/provider.py:152` `UrllibTransport` | stdlib `urllib`，**同步阻塞**；`timeout` = 两次数据间空闲超时 |
| 流式 | `core/api/provider.py:223` `complete_stream` | **同步生成器**；含重试退避 + `enable_thinking` 自动降级（`400/422`） |
| 并发编排 | `core/api/parallel.py:284` `run_parallel` | **线程池**（`threading.Thread` × N）+ `_AdaptiveLimiter`（`threading.Condition`）+ `cancel_event: threading.Event` |
| 取消语义 | `parallel.py:360` | 仅在**每个 chunk 到达后**检查 `cancel.is_set()`；阻塞在 socket 读时无法中断 |
| GUI | `gui/dialogs.py:632` `ParallelFixWorker(QThread)`；`:1030` `_request_stop` → `_cancel_event.set()` | 同上，最坏等 30s |
| CLI | `cli.py:745` `except KeyboardInterrupt` → 由 `run_parallel` 内 `thread.join(timeout=2.0)` 兜底 | 同上 |
| asyncio 使用 | 全仓库 | **零**（`grep asyncio/async def/await` 无命中） |
| `max_concurrency` 归属 | `core/api/config.py:67` | 目前**仅**由 `api/parallel.py` + GUI/CLI 读取；未见非 API 场景消费 |

### 4.2 改动范围（是否必须触碰 v1.5 的 SSE 流式层？）

**必须。** `Transport`/`_iter_lines`/`complete_stream` 是 v1.5 建立的 SSE 层，
要获得 `task.cancel()` 可打断的读，必须替换阻塞的 `urllib` 读取路径（改 `asyncio.open_connection`
或 `loop.run_in_executor`），并保留：

- chunk 间 **30s 空闲超时**语义（`provider.py:136-149`）；
- `enable_thinking` **降级**逻辑（`provider.py:281-293`，含 `_thinking_lock` 记忆）；
- 429 退避与 `on_rate_limit` 回调（供降并发）。

**连带改动面：**

| 文件 | 规模 | 改动性质 |
| :--- | ---: | :--- |
| `core/api/provider.py` | 447 行 | 高——Transport + 生成器 → async |
| `core/api/parallel.py` | 444 行 | 高——限流器/调度器/`run_parallel` → asyncio 等价物 |
| `cli.py` `_fix_todos_flow` | ~140 行 | 中——需 `asyncio.run` 驱动 |
| `gui/dialogs.py` | 1074 行 | 中高——QThread ↔ event loop 桥接（`run_coroutine_threadsafe` / `call_soon_threadsafe`），停止→`task.cancel()` |
| `tests/test_api_provider.py` / `test_api_parallel.py` / `test_cli_fix_todos.py` / `test_gui_fix.py` | — | 高——同步生成器断言全面改写（现有 `FakeTransport`/注入 `sleep` 语义基于同步） |

### 4.3 风险

| 风险 | 等级 | 说明 |
| :--- | :--- | :--- |
| 破坏 v1.5 SSE 语义 | **高** | 30s 空闲超时 / 降级记忆 / 429 退避均为既有回归测试守护项 |
| Qt 线程 + event loop 桥接 | **高** | 取消跨线程、信号线程安全，易引入难复现的 GUI 竞态 |
| 测试面重写 | 中高 | 4 个测试文件基于同步协议；改写量占本次改动相当比例 |
| 与 B1 协同度 | **低** | 追踪在**子进程**中执行 pwsh，与 API 流式层**正交**，无协同 |

### 4.4 更廉价的替代（须披露）

达成用户可感知目标「停止 <1s」**不一定需要 asyncio 重写**：
在线程模型下，让取消路径**主动关闭在途 socket**（`sock.shutdown(SHUT_RDWR)` / 关闭响应对象）
即可让阻塞的 `read()` 立即抛错返回。

- 改动面：**约 1 个文件**（cancel-aware transport + 在途句柄登记），测试面小；
- 估算：**1–2 人日**（需先做 10 分钟原型，确认 `urllib`/`HTTPResponse` 底层 socket 可被外部线程 `shutdown` 打断——**此项尚未实测，是本替代方案的唯一不确定性**）；
- 代价：保留线程模型（不引入 asyncio），未根治「架构现代化」，但**根治了遗留项 1 的用户可感知部分**。

**置信度：** 「asyncio 能达成 <1s 取消」= 高（机制确定）；
「廉价替代能达成 <1s 取消」= 中（待原型验证）；
「asyncio 为本题最优解」= **低**（高风险 + 低协同 + 有更廉价路径）。

### 5.1 机械裁定（严格按任务书裁定表）

### 5.2 偏离披露与建议（纪律 4）

**披露：本次实测发现了一条 ROI 显著更高的第三路径，与裁定表第 3 行（`.Keys/.Values` + PS 首错）同源，
但表第 3 行要求「两者皆低」才触发；而 asyncio 经 §4 评估为「中低 ROI」。

**建议将 v1.8.0 主体改为：「PS 块结构加固 + 首错收敛」**，依据：

1. **实测收益最高、可量化**：CC0 语料 60 例中，**15/60 语法失败 + 20/60 运行时失败**，
   根因收敛为 **7 类发射缺陷**（§2.2），且首两类（块栈发射 8 例、输出行未转 `echo` 4 例）
   覆盖面最大。修复后 PS 侧语法通过率可从 **75% → 95%+**，直接改善发布门槛指标。
2. **命中既有归档**：`docs/research/b3-ps-block-structure.md` 已定性 4 类**静默**结构缺陷
   （105/109/111/114，`bash -n` 全过但语义损坏，`.Keys` → 空 `for` 循环），
   并给出「先统一块栈遍历，再逐项修复」的路线与 60–90 LOC 估算——
   **本报告在 CC0 语料上独立复现了同类缺陷，佐证该路线真实且频发。**
3. **契合纪律 1**（保守 TODO 优于激进转换）：这些修复不是激进转换，而是让现状从
   「静默错误/降级」回到「正确转换或诚实 TODO」。
4. **工作量更低**：核心两类缺陷 ~1 人周可收敛；全量 7 类 ~1.5–2.5 人周
   （对照组：B1 1.5–3 人周且实测零挽回；asyncio 2–3 人周且高风险）。
5. **与「停止即时生效」不冲突**：可把遗留项 1 用 §4.4 廉价替代（1–2 人日）并入本版本，
   或明确顺延至 v1.8.1，并在 release notes 已知限制中写明。

### 5.3 请确认（执行顺序第 1 步的暂停点）

请三选一：

- **选项 1（严格按表）**：主体 = asyncio 流式层重构（2–3 人周，高风险，低协同）。
- **选项 2（本报告建议，偏离）**：主体 = PS 块结构加固 + 首错收敛
  （~1.5–2.5 人周，收益可量化）；遗留项 1 用 §4.4 廉价替代或顺延 v1.8.1。
- **选项 3（折中）**：主体 = PS 块结构加固；**同时**做 §4.4 廉价替代以根治遗留项 1 的可感知部分。

**我推荐选项 3**：既拿到最高可量化收益，又不放弃「停止即时生效」这一用户可感知项，
且规避 asyncio 重写的高风险。若你坚持裁定表的机械读法，请选选项 1，我将照办。
